Tipos de datos

Primitivos: int, float, double, char (comillas simples 'A'), bool.

Compuestos: string, arreglos (int v[5]), struct, punteros (int* p = &x).

Toda variable tiene nombre, valor (según su tipo) y dirección de memoria — esta tercera parte es la clave para entender punteros.

Que tenga dígitos no lo convierte en un número. Si un dato identifica pero no se suma ni se calcula —EAN, DNI, teléfono, código postal— conviene una cadena. En clase se trabajó con un EAN de 13 dígitos: char ean[13+1]; el espacio extra guarda el '\0'. Así también se preservan ceros iniciales y se evita desbordar un int.

Regla de oro para máximos y mínimos (Clase 03)

Todo máximo/mínimo necesita un valor inicial de comparación administrado por vos. Si la variable menorTiempo queda sin inicializar, "gana" el valor basura aleatorio que tenga la memoria. Tres formas correctas:

  • Inicializar con una cota: un valor gigante para mínimos, o muy chico para máximos.
  • Usar un valor fuera del rango (ej.: −1 si los tiempos siempre son positivos) que marque "primera vez".
  • Una marca de primera iteración: si es la primera vuelta, asignar directo sin comparar.
Con esto alcanza para escribir cualquier algoritmo sobre datos sueltos. El problema es que los datos reales vienen de a grupos: un alumno no es un número, es legajo, nombre y división juntos. Eso es un registro.

Apuntes de cátedra Structs: agrupar datos que van juntos

El ladrillo con el que se construye todo lo que sigue. Un vector de structs, un registro de archivo y el nodo de una lista son, en el fondo, la misma idea repetida en tres contextos distintos.

Qué es un registro (struct)

Un registro agrupa valores de tipos distintos (estructura heterogénea) en posiciones contiguas de memoria, bajo un único nombre. Cada valor es un campo con su identificador, y se accede con el operador punto .

struct TipoFecha {
    int d, m, a;
};                       // struct anidada (hija)

struct TipoAlumno {
    int  legajo;         // campo clave
    char nombre[40+1];   // cadena: N+1 por el '\0'
    TipoFecha fecha;     // campo que es otra struct
};                       // declara un TIPO (no reserva memoria)

TipoAlumno alumno;       // define una VARIABLE (acá sí hay memoria)
alumno.legajo   = 25;
alumno.fecha.d  = 15;    // punto encadenado en anidadas
Regla clave (repetida en Clase 02): declarar la struct hija antes que la padre. Y recordá que struct Tipo {...}; es solo una plantilla: la memoria se reserva recién al definir una variable de ese tipo.

La asignación de registro completo (clave para burbuja con structs)

La única operación que se lleva "todo junto" el registro es la asignación (reg1 = reg2), y solo si ambos son exactamente del mismo tipo (no alcanza con que tengan los mismos campos adentro). Para comparar, mostrar o leer por teclado, siempre se va campo por campo.

Clase 02: "Cuando ordeno por el campo clave pregunto por el legajo, pero el intercambio no es de un campo: el intercambio es de todo el registro." El auxiliar del swap es TipoAlumno aux; — no un int.

Struct a una función: ¿valor o referencia?

Se puede pasar por valor (se copian los datos, el original no cambia) o por referencia (se modifica el original). Buena práctica de la cátedra: pasar por referencia si la struct es grande o se va a modificar. Esto se desarrolla a fondo en la sección de punteros y referencias.

Esa última distinción, si la función recibe una copia o el original, es la que decide si tu código funciona o no. Vale la pena entenderla en serio: es el tema de punteros.

Clase grabada · 22/08 Punteros: quién puede modificar un dato

La clase construye el modelo desde memoria y direcciones; después lo aplica a new/delete, nodos, pilas, colas y listas. Esta sección separa las tres cosas que suelen confundirse: el puntero, la dirección que guarda y el dato apuntado.

La idea en una imagen

Toda variable ocupa una dirección de memoria. Un puntero es una variable cuyo valor es la dirección de otra variable. Dos operadores: & responde dónde vive una variable, y * hace lo inverso, va hasta esa dirección y trae el dato que hay ahí.

Qué pasa en memoria, línea por línea
int  x = 10;
int* p = &x;   // p guarda la dirección de x
*p = 99;       // escribo EN LA DIRECCIÓN apuntada
int  y = *p;   // leo a través del puntero
Apretá "Ejecutar" para empezar.

Tres preguntas distintas y tres formas de apuntar

ExpresiónQué responde
pLa dirección guardada: dónde vive el dato apuntado.
*pEl dato que vive en esa dirección.
&pLa dirección de la propia variable puntero.

El puntero y el dato apuntado son dos espacios de memoria distintos. Que dos punteros guarden la misma dirección no los convierte en la misma variable: ambos son caminos hacia el mismo dato.

int x = 7;
int* p = NULL;  // estado inicial conocido

p = &x;            // 1. dirección de una variable existente
p = new int;       // 2. dirección de memoria recién pedida
int* q = p;       // 3. dirección copiada desde otro int*
El tipo tiene que coincidir: un int* apunta a un int, un Alumno* a un Alumno. C++ es fuertemente tipado: no existe un “puntero genérico” para usar sin criterio.

Por valor y por referencia: la diferencia que decide todo

¿Qué le pasa a a después de llamar a la función?
// POR VALOR: viaja una COPIA
void duplicar(int n){ n = n*2; }

int a = 5;
duplicar(a);
// a sigue valiendo 5 😐
// POR REFERENCIA: viaja la variable REAL (&)
void duplicar(int &n){ n = n*2; }

int a = 5;
duplicar(a);
// a ahora vale 10

Lo que la materia usa todo el tiempo

  • Los vectores siempre viajan "por referencia": el nombre del vector es la dirección de su primer elemento (puntero constante). Por eso burbuja(v, n) ordena el original sin & — Clase 01: "el vector, ¿cómo pasa siempre en las funciones? Por referencia".
  • Variables de salida por referencia: la búsqueda binaria, el tamaño lógico real del apareo (int &k)… si la función tiene que "devolver" más de una cosa, las extra van por referencia.
  • fread(&reg, ...): el registro se pasa con & (su dirección) para que la función lo pueda llenar con lo leído del disco.
  • Prototipo, declaración e invocación deben coincidir exactamente, incluidos los &. Clase 02: "si el prototipo no es igual, tienen errores horribles; cuando usan punteros, explota pero mal".
  • Dinámica: new crea variables anónimas en tiempo de ejecución (constructores), delete las libera, y p->campo equivale a (*p).campo para structs apuntadas.

Clase grabada Memoria dinámica: new, delete y el operador flecha

Un puntero declarado sin inicializar contiene un valor indeterminado: no es seguro asumir que vale 0. Inicializalo en NULL hasta tener una dirección válida. Con new pedís memoria en tiempo de ejecución; recién entonces podés desreferenciarlo. Siempre hay dos espacios: el puntero (guarda una dirección) y el espacio apuntado (guarda el dato).

int* p = NULL; // estado inicial seguro y comprobable
p = new int;    // pido espacio → p = 0x7f3a04 (una dirección)
*p = 10;        // DESREFERENCIO: escribo en el espacio apuntado
cout << *p;     // leo a través del puntero → 10
delete p;      // LIBERO ese espacio de la memoria
p = NULL;       // evito conservar una dirección ya inválida

// con structs: (*q).campo  ≡  q->campo  (flecha, más usada)
Consulta* q = new Consulta;
q->id = 2;      // equivale a (*q).id = 2
Los tres usos del asterisco *: (1) multiplicar, (2) declarar un puntero (int* p), (3) desreferenciar — acceder al dato apuntado (*p). Para structs, q->campo es el atajo de (*q).campo; toda la cátedra usa la flecha, y el editor la autocompleta.
delete es tu responsabilidad. Las variables automáticas se liberan al salir de su ámbito; C++ no usa un recolector de basura para estos nodos. La memoria pedida con new vive hasta que hagas delete. Después, p queda colgando: ponerlo en NULL evita reutilizar accidentalmente una dirección inválida. En pilas y colas, desapilar/desencolar incluye el delete.
Sobre punteros: "un puntero es un nuevo tipo de dato que guarda un hexadecimal, y ese hexadecimal es la dirección de otra variable. Siempre están los dos espacios: el que contiene la dirección, y el lugar apuntado donde está el dato — que puede ser un entero, un float o un struct entero." La ventaja de todo esto es que habilita las estructuras dinámicas: pido memoria a medida que la necesito, sin fijar un tamaño de antemano como en el vector.

Parte II

Vectores: los cuatro patrones

Un vector es la estructura más simple que guarda muchos datos del mismo tipo, y sobre ella se aprenden los cuatro patrones que después se repiten en todas las demás: ordenar, buscar, aparear dos estructuras y recorrer por grupos. Acá el acceso al dato es trivial, v[i], y por eso conviene aprenderlos justamente acá.

Clase 01 Ordenamiento burbuja, y cuándo no usarlo

El primer patrón, con su aritmética de pasos y comparaciones. Importa tanto saber escribir burbuja como reconocer los casos en los que llamarlo es un error.

Burbuja: pasos y comparaciones

Burbuja ordena por pasos y comparaciones. En cada paso compara de a pares (posición j-1 contra j) y si el anterior es mayor, intercambia: así el más grande "burbujea" hasta el fondo. Reglas numéricas que toman en el parcial teórico:

  • Cantidad de pasos = N − 1 (vector de 5 → 4 pasos).
  • Comparaciones en el paso i = N − i (paso + comparaciones = N siempre).
  • Al terminar el paso i, los últimos i elementos ya están en su lugar → cada paso compara uno menos.
Burbuja: cómo decrecen las comparaciones en cada paso
Vector desordenado. Paso 1: el objetivo es llevar el mayor al fondo.
// La función es void: el vector pasa por referencia
void burbuja(int v[], int n){
    int aux;                     // auxiliar AFUERA de los for
    for(int i=1; i < n; i++)      // pasos: 1 .. n-1
        for(int j=1; j <= n-i; j++) // comparaciones: n-i
            if(v[j-1] > v[j]){   // el anterior vs donde estoy
                aux    = v[j-1]; // intercambio con auxiliar
                v[j-1] = v[j];
                v[j]   = aux;
            }
}
¿Por qué j arranca en 1? Para no perder la posición 0: siempre miro "el anterior de donde estoy" (v[j-1] vs v[j]). Dos iteradores independientes: i cuenta pasos, j cuenta comparaciones — cuando i crece, las comparaciones decrecen, que es exactamente la relación pasos+comparaciones=N.
El intercambio necesita una auxiliar: guardo temporalmente uno de los dos valores para que no se pise al asignar. Y la auxiliar se declara fuera de los bucles (si va adentro se re-declara en cada iteración).

Cuándo NO usar burbuja: posición única y predecible

Pregunta de examen favorita. Si los datos vienen desordenados pero están todos y pertenecen a un rango conocido (ej.: del 1 al 100, sin faltantes), no se cargan "como vienen" para después llamar a burbuja: se carga cada dato directamente en la posición que le corresponde (posición única y predecible: el valor 1 va al índice 0, el 20 al 19). Burbuja demanda recursos; PUP es una sola pasada. Burbuja aplica solo cuando no puedo predecir la posición.

Tamaño lógico vs tamaño físico

Tamaño físico = lo que reservo en memoria (int v[10]). Tamaño lógico = cuántos datos reales/utilizables tengo (quizás 7). Las funciones (burbuja, binaria, apareo) deben recibir el tamaño lógico: si paso el físico, proceso ceros o basura que no son datos válidos.

Detalle de C++ visto en vivo: int v[10] = {2}; pone el 2 en la posición 0 y llena el resto con ceros — con {0} inicializás todo el vector en cero. Pero ojo: si el 0 es un valor válido de tus datos, no te sirve como marca — hay que gestionar lógico vs físico.

Clase 02 Búsqueda binaria y el reparto de responsabilidades

Un ejercicio encadena los dos patrones: cargar un vector de structs, ordenarlo por campo clave y recién ahí buscar con búsqueda binaria. De paso aparece la idea de repartir el trabajo en funciones.

Delegar: una responsabilidad por función

El main queda limpio delegando: necesito los datos cargados → cargarDatos(v,n); los necesito ordenados → burbuja(v,n); necesito encontrarlo → busquedaBinaria(v,n,25) que devuelve la posición (no la struct — así sigue siendo la función de biblioteca que podés invocar sin desarrollar). El vector siempre viaja por referencia y cada función tiene un objetivo.

int main(){
    Alumno alumnos[N];
    cargarDatos(alumnos, N);
    burbuja(alumnos, N);                       // ordena por legajo (campo clave)
    int pos = busquedaBinaria(alumnos, N, 25);
    if(pos != -1)
        cout << alumnos[pos].nombre << " " << alumnos[pos].regional;
}
Burbuja con structs = la misma función de siempre con dos cambios: la comparación usa el campo clave (v[j-1].legajo > v[j].legajo) y el intercambio es del registro completo con un auxiliar Alumno aux (asignación de registro, mismo tipo).

Búsqueda binaria

Prerequisito: los datos ordenados (por eso primero burbuja… o mejor, PUP/carga ordenada si se puede). Divide el espacio por la mitad en cada vuelta: mantiene primero, ultimo y calcula medio adentro del while.

Búsqueda binaria: encontrar el legajo 25
int busquedaBinaria(Alumno v[], int n, int buscado){
    int primero = 0, ultimo = n-1, medio;
    while(primero <= ultimo){
        medio = (primero + ultimo) / 2;   // SIEMPRE adentro del while
        if(buscado == v[medio].legajo)
            return medio;             // lo encontré: la posición
        else if(buscado > v[medio].legajo)
            primero = medio + 1;      // está a la derecha
        else
            ultimo  = medio - 1;      // está a la izquierda
    }
    return -1;                        // no está: -1 (posición inválida)
}
Detalles corregidos en vivo (van directo al parcial de "encontrá el error"):
  • Calcular medio antes del while está de más: se calcula siempre adentro.
  • Después de preguntar por == y por >, el tercer caso no se pregunta: es un else a secas ("si no es mayor, es menor: no hay otra posibilidad" — evitás una comparación inútil).
  • ¿Por qué devuelve −1 si no está? Porque devuelve un int (posición) y −1 nunca es una posición válida.
  • La división (primero+ultimo)/2 es entera: trunca, y está bien que trunque.
Momento de debugging de la clase: un programa "que no compilaba" tenía el prototipo incoherente — recibía Alumno en vez de Alumno[], y a la binaria le faltaba el & en un parámetro por referencia. "Prototipo, invocación y declaración de la función tienen que ser exactamente iguales, si no hay errores horribles de todo tipo."
Hasta acá, todos los patrones trabajan sobre una sola estructura. El que viene trabaja sobre dos a la vez, y es el que más aparece en los finales.

Clase 03 Apareo: recorrer dos estructuras a la vez

El patrón que más veces aparece disfrazado en los finales. Según el profesor: "hubo un final donde el que se dio cuenta de que era un apareo lo resolvió en cinco minutos y se sacó un 10".

Qué es y sus precondiciones

El apareo toma dos estructuras de datos (vectores, archivos, listas — el patrón es el mismo) y produce un resultado unificado que conserva el orden. Precondiciones (las toman literalmente):

  • Ambas estructuras ordenadas bajo el mismo criterio (no una ascendente y otra descendente).
  • Con el mismo campo clave, para que sean comparables.
  • Los tamaños no tienen por qué ser iguales.

El algoritmo (3 estructuras de repetición)

void apareo(int v1[], int v2[], int v3[],
            int n, int m){
    int i=0, j=0, k=0;
    while(i < n && j < m){     // AMBOS con datos
        if(v1[i] < v2[j]){
            v3[k] = v1[i];
            i++;               // avanza el consumido
        } else {
            v3[k] = v2[j];
            j++;
        }
        k++;                   // k avanza SIEMPRE (afuera)
    }
    while(i < n){ v3[k]=v1[i]; i++; k++; } // resto de v1
    while(j < m){ v3[k]=v2[j]; j++; k++; } // resto de v2
}
La regla de avance: puedo avanzar por una estructura solo mientras tenga garantía de que hay datos (válido para vectores, archivos y listas). El while principal exige datos en ambas; cuando una se agota, se vacía la otra sin comparar nada (uno de los dos while finales se saltea solo).
¿Por qué no paso el tamaño de v3? Sin repetidos, v3 mide exactamente n+m: no necesito controlarlo. Con repetidos (si el enunciado dice "si son iguales, poné uno solo": avanzo i++ y j++ juntos, o aplico la lógica pedida), v3 puede quedar más chico → el tamaño lógico real se devuelve por referencia (int &k) para no mostrar basura después.

Clase 05 Corte de control: listar por grupos

El cuarto y último patrón. No modifica nada: sirve para mostrar datos agrupados con títulos, subtotales y totales, que es exactamente lo que piden los listados de examen.

Precondición: agrupados (¡no necesariamente ordenados!)

Cayó en un final y casi todos lo erraron: la precondición del corte de control es que los datos estén agrupados, no ordenados. Puedo tener todo el curso 8 primero, después el 4, después el 1: agrupado pero desordenado, y el corte funciona igual. Lo que sí vale: si están ordenados ⇒ están agrupados (pero no al revés).

La variable de control memoriza el grupo que estoy procesando; cuando el valor cambia, "corto": muestro el subtotal y arranco grupo nuevo.

  


  
La estructura: dos while anidados

  

    


void corteControl(Producto v[], int n){
    int i = 0, control, cont;
    float total = 0;
    while(i < n){                 // mientras haya datos
        control = v[i].provincia; // grupo que proceso
        cont = 0;                 // blanqueo el contador del grupo
        cout << "Provincia " << control << endl;  // título
        while(i < n && control == v[i].provincia){
            cout << "  " << v[i].nombre << endl;
            cont++;               // cuento / sumo / acumulo
            total += v[i].precio; // acumulador general
            i++;                  // avanzo en el vector
        }
        cout << "  Subtotal: " << cont << endl; // corte
    }
    cout << "TOTAL: " << total;   // al final de todo
}

    

    

      
Anatomía: el while externo itera "mientras haya datos" (común a todos los algoritmos). Adentro: asigno la variable de control con el grupo actual, blanqueo contadores del grupo, y el while interno procesa mientras haya datos Y no cambie el grupo. Al salir del interno (cambió el grupo o se acabaron los datos) emito el subtotal — control todavía tiene el grupo viejo, por eso puedo mostrarlo.

      
La condición del while interno pregunta primero i < n y después el grupo — en ese orden, para no leer v[i] fuera del vector.

      
Puede haber varios niveles de agrupamiento (provincia → ciudad): se anidan más whiles con más variables de control. Y el "valor agregado" puede ser contar, sumar, promediar (sumo y cuento, divido al cortar) o porcentajes.

fread y fwrite: lectura/escritura por bloques


int leidos = fread(&reg, sizeof(reg), 1, f);
//                 │        │          │  └ archivo (nombre lógico)
//                 │        │          └ cantidad de bloques (casi siempre 1)
//                 │        └ tamaño del bloque: sizeof del registro
//                 └ DIRECCIÓN de memoria donde dejar lo leído (& = por referencia)

  • fread funciona como cinta lectora: lee los bytes del bloque y el puntero del archivo queda al final del registro leído → la próxima lectura trae el siguiente. Lo mismo al escribir.
    • 
    
  • Retorna la cantidad de bloques que pudo leer (o menos): si pido 1 y estoy al final, retorna 0. Devuelve dos cosas: por el nombre la cantidad, y por el parámetro (referencia) el registro leído.
    • 
    
  • Si en memoria tengo un vector de registros, puedo leer varios juntos: fread(v, sizeof(TipoReg), 4, f) — el nombre del vector ya es dirección, sin &.
    • 
    
  • sizeof aplicado a una variable o tipo devuelve su tamaño en bytes: es la manera correcta de indicar el bloque.
    • 
  


  
feof: la marca de fin de archivo

  
El final del archivo está después del último registro. Cuando un fread intenta leer ahí, retorna 0 y la marca feof(f) pasa a verdadera. Por eso el patrón de recorrido usa lectura anticipada:


fread(&reg, sizeof(reg), 1, f);      // lectura anticipada
while(!feof(f)){
    procesar(reg);                   // uso el registro que YA leí
    fread(&reg, sizeof(reg), 1, f);  // intento leer el próximo
}

  
Si preguntara feof antes de leer, procesaría el último registro dos veces o basura: la marca se activa recién al intentar leer más allá del último.

Modificar un registro: apuntar → leer → modificar → re-apuntar → grabar

  
En un vector, modificar es una línea (v[n].campo = x). En un archivo son 5 pasos, porque después de leer el puntero avanzó:


fseek (f, n*sizeof(r), SEEK_SET);   // 1. apunto al registro n
fread (&r, sizeof(r), 1, f);        // 2. lo traigo a memoria (el puntero avanzó!)
r.campo1 = nuevoValor;              // 3. modifico EN MEMORIA
fseek (f, -(int)sizeof(r), SEEK_CUR); // 4. retrocedo un registro (el truco elegante)
fwrite(&r, sizeof(r), 1, f);        // 5. grabo encima del original

  
Si te salteás el paso 4, fwrite pisa el registro siguiente. El retroceso puede hacerse con SEEK_CUR y bytes negativos (lo propuso un alumno y el profesor lo celebró) o re-apuntando con SEEK_SET.


  
fclose y el buffer

  
Al grabar, los datos van primero a un buffer en memoria y se vuelcan al disco cuando el buffer se llena. fclose(f) vuelca lo que quede pendiente: si no cerrás, los últimos registros pueden no grabarse. Siempre: abrir al comienzo, cerrar al final.

Ordenar un archivo: por qué el acceso directo (y no fread suelto)

  
Para ordenar un archivo, la tentación es leer registro por registro con fread secuencial e ir guardando cada valor donde va. Pero eso es ineficiente (abrir/recorrer el archivo muchas veces cuesta caro a nivel computacional) y encima, si no sé la longitud del archivo, ¿cómo lo dimensiono? La forma correcta es acceso directo: hago lo mismo que con un vector — traigo todo a memoria, ordeno con burbuja y regrabo.

  
PUP también aplica a archivos. Igual que en un vector el elemento de clave k va en V[k-1], en un archivo la posición del registro k se calcula en bytes: (k-1) × sizeof(TipoReg), y ahí apuntás con fseek(f, (k-1)*sizeof(TipoReg), SEEK_SET) antes de escribir/leer.


  
El problema del huevo y la gallina: para volcar el vector de una sola pasada con fwrite(v, sizeof(TipoReg), cantReg, f) necesito saber cuántos registros hay… pero no sé ni el tamaño del archivo ni la cantidad de registros. La solución es una función cantReg que lo calcula con ftell y sizeof (la fórmula de la sección anterior), dejando el puntero donde estaba.


  

    


// Devuelve cuántos registros tiene el archivo,
// sin alterar la posición del puntero.
int cantReg(FILE* f){
    int posActual = ftell(f);   // 1. dónde estaba
    int cantRegistros = 0;
    fseek(f, 0, SEEK_END);      // 2. voy al final
    int tam = ftell(f);          // 3. bytes totales
    cantRegistros = tam / sizeof(articulo); // 4. /tamaño de un reg
    fseek(f, posActual, SEEK_SET); // 5. restauro el puntero
    return cantRegistros;
}

Para aparear dos archivos no conviene cargar ambos en vectores: es impráctico. void apareo(FILE* f1, FILE* f2, FILE* f3){
    fseek(f1, 0, SEEK_SET); fseek(f2, 0, SEEK_SET); fseek(f3, 0, SEEK_SET);
    str r1, r2;
    fread(&r1, sizeof(str), 1, f1);      // lectura inicial de cada uno
    fread(&r2, sizeof(str), 1, f2);
    while(!feof(f1) && !feof(f2)){   // mientras ambos tengan registros
        if(r1.id < r2.id){
            fwrite(&r1, sizeof(str), 1, f3);
            fread (&r1, sizeof(str), 1, f1);  // avanzo el consumido
        } else {
            fwrite(&r2, sizeof(str), 1, f3);
            fread (&r2, sizeof(str), 1, f2);
        }
    }
    while(!feof(f1)){                   // agotar f1
        fwrite(&r1, sizeof(str), 1, f3);
        fread (&r1, sizeof(str), 1, f1);
    }
    while(!feof(f2)){                   // agotar f2
        fwrite(&r2, sizeof(str), 1, f3);
        fread (&r2, sizeof(str), 1, f2);
    }
}

  
Es exactamente el apareo de vectores (comparo cabezas, consumo el menor, vuelco el resto), pero avanzar = fread y guardar = fwrite, y "hay datos" se pregunta con !feof. Después, si lo necesitás, pasás del archivo apareado a un vector. Mismo patrón, distinto acceso al dato.

Memoria dinámica: el dato que crece

  
El vector obliga a decidir el tamaño antes de saberlo y el archivo es lento. Cuando no sabés cuántos elementos vas a tener, la salida es pedir memoria a medida que llega cada dato y encadenarla. Clase grabada Listas enlazadas

  
El tema central del segundo parcial y del final. Una lista se arma con el mismo nodo que una pila o una cola, con la diferencia de que acá podés insertar y sacar donde quieras.


  
Estático vs dinámico

  
Las estructuras estáticas (vectores) reservan memoria fija al declararse. Las dinámicas piden memoria en tiempo de ejecución con new (y la liberan con delete), a través de punteros. Sirven cuando no sé cuántos elementos voy a tener: la lista crece nodo a nodo a medida que llegan los datos.


  
El nodo y la lista

  

    


struct Nodo {
    TipoInfo info;      // los datos (una struct)
    Nodo* sig;          // puntero al siguiente nodo
};                      // struct AUTOREFERENCIADA

Nodo* lista = NULL;     // lista vacía: puntero a NULL

      
Cada nodo apunta al siguiente; el último apunta a NULL. El acceso a los campos de un nodo apuntado es con la flecha: p->info (equivale a (*p).info).

    

    

      
Recorrido estándar (el que se usó en Clase 09):

Nodo* p = lista;        // auxiliar: nunca muevo "lista"
while(p != NULL){
    mostrar(p->info);
    p = p->sig;         // avanzar = seguir la flecha

insertarOrdenado: los tres casos

  
Toda la lógica de mantener la lista ordenada al insertar se reduce a tres casos (clase del 12-09). La función recibe la lista por referencia (Nodo*&, porque el puntero puede cambiar) y la info; el armado del nodo lo hace ella.

  

    

      
Caso 1 — lista vacía (lista == NULL): creo el nodo, su sig apunta a NULL (que es lo que vale la lista), y la lista pasa a apuntarlo.

      
Caso 2 — el valor es menor que el primero: el nodo nuevo va adelante. Primero enlazo su sig a donde apuntaba la lista (para no perder el resto), y después la lista apunta al nodo nuevo. Casos 1 y 2 son idénticos a un push de pila — por eso se unifican.

      
Caso 3 — va en el medio: avanzo con un auxiliar buscando dónde el siguiente es mayor. Como la lista ya está ordenada, no hace falta preguntar por el anterior: en cuanto aux->sig->info > valor, ese es el lugar. Enlazo primero nuevo->sig = aux->sig (no pierdo lo que viene) y después aux->sig = nuevo.

    

    


Nodo* insertarOrdenado(Nodo*& lista, Info dato){
    Nodo* nuevo = new Nodo;   // armo el nodo (lo hace la función)
    nuevo->info = dato;
    // Casos 1 y 2: lista vacía o va adelante
    if(lista == NULL || dato.clave < lista->info.clave){
        nuevo->sig = lista;      // enlazo antes de mover
        lista = nuevo;           // re-apunto la cabeza
    } else {
        // Caso 3: buscar el lugar en el medio
        Nodo* aux = lista;
        while(aux->sig != NULL &&
              aux->sig->info.clave < dato.clave)
            aux = aux->sig;
        nuevo->sig = aux->sig;    // no pierdo lo que viene
        aux->sig   = nuevo;       // re-enlazo
    }
    return nuevo;               // puedo ignorarlo o usarlo como enganche
}

    

  

  
El orden de los dos enlaces es sagrado: siempre primero conectás el nodo nuevo a lo que viene, y después movés el puntero anterior. Si lo hacés al revés, "cortás" la lista y perdés todos los nodos que seguían.

buscar(listaLP, clave) — recorrido secuencial que devuelve un puntero


nodoLP* buscar(nodoLP* listaLP, int clave){
    nodoLP* q = listaLP;                    // auxiliar: NO muevo la cabeza original
    while(q != NULL && q->info.division != clave)
        q = q->sgte;                        // avanzar = seguir la flecha
    return q;      // el nodo encontrado, o NULL si no está
}

    
    
      
  • Recibe la lista por valor (nodoLP*, sin &): no modifica la lista, solo la mira. Copiar el puntero es inofensivo.
    • 
      
  • El orden de la condición importa: primero q != NULL y después q->info. Si preguntaras al revés, al llegar al final harías NULL->info y el programa explota.
    • 
      
  • Devuelve el puntero, no un bool. Esta es la clave de toda la sección: necesito el nodo en sí para colgarle la sublista. Un "sí/no" no me serviría.
    • 
      
  • Al salir del while, q ya vale exactamente lo que hay que devolver: el nodo hallado, o NULL si se recorrió todo. No hace falta un if final.
    • 
    

    
Es búsqueda secuencial: en una lista no hay índices, así que no existe la binaria. Como la lista está ordenada por división, se podría cortar antes con q->info.division < clave — una optimización válida que no cambia el resultado.

  


  
insertarOrdenadoLP(listaLP, dato) — los tres casos, con & en la lista


nodoLP* insertarOrdenadoLP(nodoLP*& listaLP, infoLP dato){
    nodoLP* nuevo = new nodoLP;   // pido memoria
    nuevo->info = dato;                // asignación de struct completo
    nuevo->sgte = NULL;

    if(listaLP == NULL || dato.division < listaLP->info.division){
        nuevo->sgte = listaLP;    // CASOS 1 y 2: enlazo al viejo primero…
        listaLP     = nuevo;      // …y recién ahí muevo la cabeza
    } else {                                  // CASO 3: medio o final
        nodoLP* anterior = listaLP;
        nodoLP* actual   = listaLP->sgte;
        while(actual != NULL && actual->info.division < dato.division){
            anterior = actual;
            actual   = actual->sgte;   // avanzan de a pares
        }
        nuevo->sgte    = actual;       // 1º: no pierdo lo que viene
        anterior->sgte = nuevo;        // 2º: engancho por atrás
    }
    return nuevo;   // ← devuelve el nodo recién creado
}

    

      

        
Caso 1 — lista vacía. listaLP == NULL: el nuevo apunta a NULL (que es lo que vale la lista) y pasa a ser la cabeza.

        
Caso 2 — va antes del primero. dato.division < primera: idéntico al caso 1, por eso se unifican con ||. Es exactamente un push de pila.

        
Caso 3 — medio o final. Avanzo con dos punteros (anterior y actual) hasta que actual sea mayor o se acabe la lista. Ahí, el nuevo va justo entre los dos.

      

      

        
Por qué nodoLP*& (por referencia). En los casos 1 y 2 la cabeza cambia. Si la lista viajara por valor, modificarías una copia y el main seguiría viendo NULL: perderías todo. En el caso 3 no cambia la cabeza, pero la firma debe contemplar el peor caso.

        
El orden de los dos enlaces es sagrado. Primero nuevo->sgte = actual, después anterior->sgte = nuevo. Al revés, perdés el puntero a todo el resto de la lista.

        
¿Por qué anterior arranca en listaLP y actual en listaLP->sgte? Porque si llegué al else, ya sé dos cosas: la lista no está vacía y el dato no va antes del primero. Entonces el primer nodo ya es un "anterior" válido y puedo desreferenciar listaLP->sgte sin riesgo.

      

    

  


  
insertarSinRepetir(listaLP, dato) — el corazón de la lista de listas


nodoLP* insertarSinRepetir(nodoLP*& listaLP, infoLP dato){
    nodoLP* aux = buscar(listaLP, dato.division);
    if(aux == NULL)                                // no existía…
        aux = insertarOrdenadoLP(listaLP, dato);   // …la creo y me quedo con su dirección
    return aux;   // SIEMPRE devuelve el nodo de esa división
}

    
Son cinco líneas y resuelven el patrón "existe → lo recupero; no existe → lo creo y lo recupero". Salgas por donde salgas, tenés en la mano el mismo tipo de resultado: el puntero al nodo de esa división. Ese puntero es el punto de enganche para todo lo que sigue.

    
Consecuencia clave que se pregunta en el examen: si la división ya existía, el dato que armaste (con contador = 0 y listaS = NULL) se descarta: nunca se copia sobre el nodo existente. Por eso el contador no se reinicia y la sublista no se pierde. Los valores iniciales solo se usan si el nodo se crea.

  


  
insertarOrdenadoLS(listaLS, dato) — la misma función, otro nivel

    
Es letra por letra la misma lógica que insertarOrdenadoLP, cambiando tres cosas: el tipo de nodo (nodoLS), la clave de comparación (legajo en vez de division) y la info que guarda.

    nuevo->info = dato;

    2.

    Como auxLP es un puntero al nodo real (no una copia), el ++ modifica la lista de verdad. Acá se ve por qué buscar tenía que devolver un puntero.
    3. 
      
  3. insertarOrdenadoLS(auxLP->info.listaS, datoLS);
    El truco central: le paso un campo de un nodo como si fuera una lista suelta. Y lo es: auxLP->info.listaS es un nodoLS*, y viaja por referencia, así que si el alumno entra primero, la cabeza de esa sublista se actualiza dentro del nodo de la división. Esto es "lista de listas" en una línea.
    4. 
    

    
strcpy y no =: apellidoNombre es un char[]. Los arreglos no se copian con el operador de asignación; se usa strcpy (de <cstring>). En cambio nuevo->info = dato; sí funciona, porque ahí se copia un struct completo del mismo tipo — y al copiarlo, el char[] de adentro viaja incluido.

void mostrarListado(nodoLP* listaP){

        p = p->sgte;                 // paso a la división siguiente
    }
}

liberarListas(listaP) — de adentro hacia afuera


void liberarListas(nodoLP*& listaP){
    while(listaP != NULL){
        nodoLS* alumnoActual = listaP->info.listaS;
        while(alumnoActual != NULL){           // 1º vacío la SUBLISTA
            nodoLS* borrarAlumno = alumnoActual;  //    me guardo a quién borrar
            alumnoActual = alumnoActual->sgte;     //    AVANZO antes de borrar
            delete borrarAlumno;                   //    recién ahí libero
        }
        nodoLP* borrarDivision = listaP;          // 2º recién ahora la división
        listaP = listaP->sgte;
        delete borrarDivision;
    }                                             // listaP queda en NULL
}

    

      

        
El orden de los dos niveles no es opcional. Si borraras primero el nodo de la división, perderías listaS — el único puntero a esa sublista — y sus nodos quedarían ocupando memoria para siempre, inalcanzables (memory leak). Siempre: hijos primero, padre después.

      

      

        
Avanzar antes de borrar. El trío guardar → avanzar → delete se repite en los dos niveles. Si hicieras delete p; p = p->sgte; estarías leyendo un nodo ya destruido: comportamiento indefinido.

        
Por qué nodoLP*&: al terminar, la cabeza debe quedar en NULL en el main. Si viajara por valor, el main conservaría un puntero a memoria liberada (dangling pointer) — una bomba de tiempo.

Clase grabada Pilas y colas: listas con reglas

  
Mismo nodo que la lista, mismas flechas, pero con casi todas las operaciones prohibidas. Lo único que cambia es el orden en que se guarda y se recupera, y de ahí sale todo lo que sirven.


  
Regla que reprueba un parcial si se rompe (dicha textual en clase): pila y cola NUNCA, JAMÁS se recorren. Con una pila solo podés hacer tres cosas: preguntar si está vacía (== NULL), apilar y desapilar. Con una cola: preguntar si está vacía, encolar y desencolar. Recorrer una pila/cola, o pasar una cola con un solo puntero, es "examen anulado, un 2 fijo".

  

    

      
Pila, LIFO

      
Last In, First Out: el último en entrar es el primero en salir. Solo se opera por un extremo (el tope): apilar (push) y desapilar (pop). Como una pila de platos.

      

    

    

      
Cola, FIFO

      
First In, First Out: el primero en entrar es el primero en salir. Se encola por un extremo y se desencola por el otro. Como la fila del banco.

      

    

  

  
El nodo (compartido) y la declaración

  

    


struct Nodo {
    Alumno info;    // info: un struct (no un simple int)
    Nodo*  sig;     // puntero al siguiente → AUTOREFERENCIADA
};

Nodo* pila = NULL;   // una pila es un puntero a nodo, inicia en NULL

      
Inicializar en NULL no es opcional. "Preguntar si está vacía es preguntar por un NULL"; si no la inicializás, ese chequeo falla y todo se rompe.

    

    

      
apilar (push) — 3 pasos: (1) pedir memoria y armar el nodo (new), (2) guardar la info, (3) re-apuntar. La pila se pasa por referencia porque su puntero cambia con cada push.

void push(Nodo*& pila, Alumno dato){
    Nodo* p = new Nodo;  // 1. pido memoria
    p->info = dato;         // 2. guardo la info
    p->sig  = pila;         // 3. el nuevo apunta al viejo tope
    pila    = p;            //    la pila apunta al nuevo
}

    

  

  
desapilar (pop): tomo el nodo del tope, extraigo su info y se la devuelvo al usuario, muevo la pila a pila->sig y hago delete del nodo. Recuperar información de una pila implica destruir el nodo: no hay forma de "leer sin sacar".

  
Ver el código de pop y el orden “preservar → re-apuntar → borrar”


Alumno pop(Nodo*& pila){
    Nodo* p = pila;       // 1. preservo el nodo que voy a borrar
    Alumno dato = p->info; // 2. preservo la información a devolver
    pila = p->sig;         // 3. re-apunto al nodo anterior
    delete p;             // 4. libero el viejo tope
    return dato;
}

    
La función supone que hay un nodo. La condición pila != NULL se controla antes de invocarla; desreferenciar una pila vacía sería acceder a memoria inválida.

  


  

    
Apilar y desapilar: el tope es lo único accesible

    

    
    

    

      
      
      
    

    
Pila vacía (NULL). El último que entra es el primero que sale.

Para insertar X en la tercera posición, pasás los dos primeros a una pila auxiliar, apilás X y devolvés los dos datos. El segundo traslado restaura su orden original.

La inversión puede ser el objetivo, no un problema. En el ejercicio de clase con una cadena como ABC.CBA, se apila lo que está antes del punto y después se compara cada carácter restante con un pop. La propiedad LIFO entrega C, B, A sin índices hacia atrás ni una segunda copia del vector.


  
Cola: por qué necesita DOS punteros

  
En una pila entra y sale por el mismo lado, así que alcanza un puntero. En una cola entra por el fondo y sale por el frente — y como no se puede recorrer, necesito dos punteros: frente (de dónde saco) y fin (dónde engancho al que llega). Ambos inician en NULL.

  

    


Nodo* frente = NULL;
Nodo* fin    = NULL;

void encolar(Nodo*& frente, Nodo*& fin, Alumno dato){
    Nodo* p = new Nodo;
    p->info = dato;
    p->sig  = NULL;        // va al final: nadie después de él
    if(frente == NULL)     // cola vacía: frente y fin
        frente = p;         //   apuntan al mismo nodo
    else
        fin->sig = p;        // enlazo el viejo último con el nuevo
    fin = p;                // fin siempre apunta al recién llegado
}

    

    

      
El orden importa de nuevo: cuando llega un nodo, primero enlazo fin->sig = p (conecto el viejo último al nuevo) y recién después muevo fin = p. Si movés fin antes, perdés la conexión y partís la cola al medio.

      
desencolar: saco por frente, devuelvo su info, avanzo frente = frente->sig y hago delete. Si la cola queda vacía, fin también vuelve a NULL.

      
Consumir una cola en el examen (patrón del Final): mientras no esté vacía, desencolo, proceso la info, sigo. Se va vaciando — mismo "mientras haya datos" de siempre.

    

  

  
Ver desencolar y el caso especial del último nodo


Alumno desencolar(Nodo*& frente, Nodo*& fin){
    Nodo* p = frente;
    Alumno dato = p->info;
    frente = p->sig;

    if(frente == NULL) // saqué el último: la cola quedó vacía
        fin = NULL;       // ambos punteros deben reflejarlo

    delete p;
    return dato;
}

    
La cola tiene dos excepciones simétricas: al encolar el primero, frente y fin apuntan al mismo nodo; al desencolar el último, ambos vuelven a NULL.

  


  
"Si tenés una cola y le pasás un solo puntero, eso es directamente un examen anulado, un 2 fijo. Van dos punteros: frente y fin."


  
Aparear colas es más delicado que aparear vectores o listas. Las colas deben estar ordenadas, pero no podés mirar frente->info: tenés que desencolar y conservar cada cabeza en una variable. Una cola puede quedar en NULL y, aun así, quedar un dato pendiente en esa variable. Por eso el control del apareo considera dos estados: si quedan nodos y si ya hay una cabeza extraída sin procesar. El resultado se construye únicamente con encolar.


  
Otras dinámicas que existen (solo concepto, para el teórico): listas circulares, doblemente enlazadas, árboles, árboles binarios de búsqueda, AVL, tablas hash, grafos. En esta materia se ven pilas, colas y listas; si hay tiempo, una introducción a árboles (útil para bases de datos).

  
Con vectores, archivos y estructuras dinámicas sobre la mesa, lo que queda es lo que realmente toman: combinarlas para resolver un problema con contexto.

Clase 09 De un archivo a un vector de listas

  
Un ejercicio de examen resuelto en clase que junta las tres partes anteriores: se lee un archivo, se ubica por posición predecible en un vector y cada posición cuelga una lista que se mantiene ordenada sola.


  
El enunciado

  

    
Un archivo (ya abierto, lo recibís por parámetro) con registros {idSucursal, idEmpleado, importe}, todo mezclado. Se pide un listado por sucursal y, dentro de cada una, sus vendedores ordenados con lo vendido. Las sucursales son N, están todas numeradas → posición única y predecible. Los vendedores: no sé cuántos son ni qué números tienen → estructura dinámica.

  


  
La estructura ganadora: un vector de listas

  

  
  


  
La solución completa (≈10 líneas de lógica)


struct DatoArchivo { int idSucursal; int idEmpleado; float importe; };
struct Info        { int idEmpleado; float importe; };  // info de cada nodo

void llenarVector(FILE* f, NodoLista* vector[], int n){
    DatoArchivo reg;  Info info;
    fread(&reg, sizeof(reg), 1, f);              // lectura anticipada
    while(!feof(f)){
        info.idEmpleado = reg.idEmpleado;        // preparo la info del nodo
        info.importe    = reg.importe;
        insertarOrdenado(vector[reg.idSucursal - 1], info); // PUP + delegación
        fread(&reg, sizeof(reg), 1, f);
    }
}

void mostrar(NodoLista* vector[], int n){
    for(int i=0; i<n; i++){
        cout << "Sucursal " << i+1 << endl;     // posición ↔ id: i+1
        NodoLista* p = vector[i];                // auxiliar para no perder la lista
        while(p != NULL){
            cout << "  " << p->info.idEmpleado << ": $" << p->info.importe << endl;
            p = p->sig;
        }
    }
}

  
Puntos que el profesor remarcó al corregir en vivo:
  
    
    
  • vector[reg.idSucursal - 1]: la sucursal 1 va a la posición 0 — el clásico −1 de la PUP.
    • 
    
  • insertarOrdenado devuelve un puntero al nodo, pero acá se usa como void: no siempre necesitás lo que retorna una función.
    • 
    
  • Después de insertar no hay que "avanzar" nada a mano: la PUP te ubica y la función gestiona los nodos. Error común: agregar índices que no van.
    • 
    
  • En el examen, las funciones de biblioteca se invocan con el prototipo adecuado a tus tipos (insertarOrdenado(NodoLista*&, Info)), sin desarrollarlas.
    • 
    
  • Mostrar sin vaciar: recorrido con auxiliar. Si pidieran vaciar, se usa extraerPrimero hasta NULL.
    • 
  

  
"Se cumplió el objetivo con la cantidad mínima de código. Los exámenes son compactitos: pocas líneas si elegís bien las estructuras."

Enunciado (resumen fiel)

    
Una web de streaming. Se dispone de:

    
    
      
  • A) Archivo usuarios.dat ordenado por idUsuario, con registros struct Usuarios { int idUsuario; char nombreUsuario[250+1]; char mail[100+1]; }.
    • 
      
  • B) Una cola de visualizaciones: nodos struct InfoVisualizacion { int idPelicula; char nombrePelicula[100+1]; int idUsuario; }. Un usuario ve muchas películas distintas; nunca la misma repetida.
    • 
    

    
Se pide cargar una lista de usuarios donde cada nodo tenga: id, nombre, cantidad total de películas vistas y una sublista de películas (id + nombre). Se pueden invocar las funciones de biblioteca sin desarrollarlas (con el prototipo con tus tipos si no usás templates).

  


  
Punto 1 · Definición de los tipos de datos (1 punto)

  
Cómo pensarlo: hay dos niveles de lista → dos "info" y la sublista vive adentro del info del nivel superior. Recordá: struct hija antes que la padre, y el campo de la sublista es un puntero al nodo de películas.

  
Ver solución del punto 1


// ---- nivel película (sublista) ----
struct InfoPelicula {
    int  idPelicula;
    char nombrePelicula[100+1];
};
struct NodoPelicula {
    InfoPelicula  info;

};

// ---- nivel usuario (lista principal) ----
struct InfoUsuario {

    InfoUsuario  info;

Por qué vale 1 punto pero importa el doble: "si definen mal las estructuras de datos, tienen una visión incorrecta del problema" — todo lo que sigue depende de esto.

  


  
Punto 2 · obtenerListaUsuarios (2 puntos)

  
Cómo pensarlo: es el patrón "recorrer archivo y llenar estructura" de la Clase 09, con un detalle regalado: el archivo ya viene ordenado por idUsuario → insertando al final (o al principio y no importa, mejor al final) la lista queda ordenada sola. Lectura anticipada + preparar la info + delegar en la biblioteca. Sublistas vacías = NULL, contador en 0.

  
Ver solución del punto 2


NodoUsuario* obtenerListaUsuarios(FILE* f){
    NodoUsuario* lista = NULL;
    Usuarios    reg;
    InfoUsuario info;

    fread(&reg, sizeof(Usuarios), 1, f);        // lectura anticipada
    while(!feof(f)){
        info.idUsuario = reg.idUsuario;          // preparo la info
        strcpy(info.nombreUsuario, reg.nombreUsuario);
        info.cantPeliculas = 0;                  // pedido: contador en 0

Punto 3 · cargarPelicula (3 puntos)

  
Cómo pensarlo: recibe la lista de usuarios y UNA InfoVisualizacion. Hay que (1) buscar el nodo del usuario recorriendo la lista, (2) armar la info de película, (3) insertarla en su sublista, (4) incrementar su contador. La sublista de un nodo se pasa como p->info.peliculas — ahí está la gracia del ejercicio.

  
Ver solución del punto 3


void cargarPelicula(NodoUsuario* lista, InfoVisualizacion v){
    // 1. busco el usuario (búsqueda secuencial en la lista)
    NodoUsuario* p = lista;
    while(p != NULL && p->info.idUsuario != v.idUsuario)
        p = p->sig;

    if(p != NULL){                            // lo encontré
        // 2. preparo la info de la película
        InfoPelicula ip;
        ip.idPelicula = v.idPelicula;
        strcpy(ip.nombrePelicula, v.nombrePelicula);
        // 3. la agrego a SU sublista (delego en la biblioteca)
        insertarUltimo(p->info.peliculas, ip);
        // 4. actualizo SU contador
        p->info.cantPeliculas++;
    }
}

    
Como la lista está ordenada por id, podrías cortar la búsqueda cuando p->info.idUsuario > v.idUsuario (optimización que suma). El orden de la sublista no está exigido: insertarUltimo o insertarPrimero valen; insertarOrdenado por idPelicula también, y te regala el punto 4.

  


  
Punto 4 · tienenGustosSimilares (4 puntos)

  
Cómo pensarlo: recibe DOS sublistas de películas y retorna true si comparten al menos 5. Es contar coincidencias entre dos estructuras… ¿te suena? Si ambas sublistas están ordenadas por idPelicula es un apareo puro (el famoso final que se resolvía en 5 minutos). Si no asumís orden, es doble recorrido O(n·m). Ambas valen; el apareo es la elegante.

  
Ver solución del punto 4 (versión apareo)


// Asumiendo sublistas ordenadas por idPelicula
// (las generé con insertarOrdenado en el punto 3 y lo anoto en el examen)
bool tienenGustosSimilares(NodoPelicula* a, NodoPelicula* b){
    int comunes = 0;
    while(a != NULL && b != NULL && comunes < 5){
        if(a->info.idPelicula == b->info.idPelicula){
            comunes++;               // coincidencia: avanzo los dos
            a = a->sig;
            b = b->sig;
        } else if(a->info.idPelicula < b->info.idPelicula)
            a = a->sig;              // avanza el menor (regla del apareo)
        else
            b = b->sig;
    }
    return comunes >= 5;
}


Ver también la versión sin orden (doble recorrido)


bool tienenGustosSimilares(NodoPelicula* a, NodoPelicula* b){
    int comunes = 0;
    for(NodoPelicula* p = a; p != NULL; p = p->sig)
        for(NodoPelicula* q = b; q != NULL; q = q->sig)
            if(p->info.idPelicula == q->info.idPelicula)
                comunes++;   // no hay repetidas dentro de un usuario
    return comunes >= 5;
}



    
Los tres avances del apareo (iguales: los dos; si no: el menor) aplican idénticos a listas — solo cambió i++ por p = p->sig. El corte anticipado comunes < 5 es un plus de eficiencia.
